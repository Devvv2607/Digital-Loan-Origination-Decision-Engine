# Deploying Lendwise (Demo)

> Demo prototype. Simulated integrations and synthetic data. Not affiliated with any bank or lender.

Three free services: **Neon** (Postgres), **Render** (FastAPI backend, configured by `render.yaml`), **Vercel** (Next.js frontend). A GitHub Actions schedule runs the expiry job. Nothing secret goes into the repository; every secret is typed into a host's dashboard.

Order matters: database → backend → frontend → CORS update → GitHub secrets.

---

## Part A — Neon (database)

1. Sign in at [neon.tech](https://neon.tech) and click **New project**.
2. Name it `lendwise-demo`, choose Postgres 16 or newer, and pick the region **AWS Asia Pacific (Singapore)** (the backend runs in Render's Singapore region).
3. Click **Create project**.
4. On the project dashboard, click **Connect**. Leave the database as `neondb` and the role as the default owner.
5. **Turn connection pooling OFF** (the "Connection pooling" toggle), so the host name does **not** contain `-pooler`. The backend uses psycopg 3, whose prepared statements don't work through the pooler's transaction mode, and migrations need a direct connection.
6. Copy the connection string. It looks like `postgresql://neondb_owner:...@ep-xxxx.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`. Keep it to hand for step 11; don't paste it anywhere else. (The `postgresql://` prefix is fine: the app switches it to the psycopg 3 driver.)

## Part B — Render (backend API)

7. Sign in at [render.com](https://render.com) with GitHub, and allow Render to access the `Digital-Loan-Origination-Decision-Engine` repository.
8. Click **New +** → **Blueprint**.
9. Select the repository and branch `main`. Render reads `render.yaml` and shows one web service, `lendwise-demo-api` (free plan, Singapore).
10. Give the Blueprint a name (for example `lendwise-demo`).
11. Render asks for the values marked `sync: false`. Enter:

    | Key | Value |
    |---|---|
    | `DATABASE_URL` | the Neon connection string from step 6 |
    | `ADMIN_PASSWORD` | a new password, at least 8 characters, not containing `change-me` |
    | `OPS_PASSWORD` | a different new password, same rules |
    | `CORS_ORIGINS` | `http://localhost:3000` for now (replaced in step 24) |

    Everything else comes from `render.yaml`: `ENV=production`, `DEMO_SEED=true`, read-only demo mode, usernames `admin` and `ops`, and `JWT_SECRET` and `PII_HASH_KEY` generated by Render. Keep the two passwords in your password manager.
12. Click **Apply**. The first build installs the Python packages (a few minutes). On start, the service runs the database migrations, then loads policy version 1 and the 500 seeded demo applications into the empty database.
13. When the deploy shows **Live**, copy the service URL from the top of the service page, for example `https://lendwise-demo-api.onrender.com`.
14. Check it: open `https://<your-render-url>/health`. Expect `"status": "ok"`, `"database": "ok"`, `"policy_version": 1` and `"clock": {"kind": "system", ...}`.
15. Check the seed: open `https://<your-render-url>/metrics/funnel`. The first stage should show `"count": 500`.
16. Swagger is at `https://<your-render-url>/docs`.

If the deploy fails, open **Logs**. A configuration problem prints `Invalid configuration` followed by the variable names to fix (see Troubleshooting).

## Part C — Vercel (frontend)

17. Sign in at [vercel.com](https://vercel.com) with GitHub.
18. Click **Add New…** → **Project**, then **Import** the `Digital-Loan-Origination-Decision-Engine` repository.
19. Set **Root Directory** to `frontend` (click **Edit** next to it). Vercel should detect **Next.js**; leave the build settings as they are.
20. Under **Environment Variables**, add `NEXT_PUBLIC_API_URL` with the Render URL from step 13, **without** a trailing slash (for example `https://lendwise-demo-api.onrender.com`).
21. Click **Deploy**.
22. When it finishes, copy the production URL, for example `https://lendwise-demo.vercel.app` (shown under **Domains** on the project page).

`NEXT_PUBLIC_API_URL` is built into the frontend. If you change it later, redeploy the frontend (**Deployments** → latest → **Redeploy**).

## Part D — CORS update (after Vercel is live)

The backend only accepts browser requests from the origins in `CORS_ORIGINS`, so it must now allow the Vercel site.

23. In Render, open the `lendwise-demo-api` service → **Environment**.
24. Edit `CORS_ORIGINS` and set it to the Vercel URL from step 22: `https://lendwise-demo.vercel.app`. Use the exact origin: `https://`, no trailing slash, no path. To also allow local development, separate origins with a comma: `https://lendwise-demo.vercel.app,http://localhost:3000`.
25. Click **Save Changes**. Render redeploys the service automatically (about a minute). The data is kept: the seed only loads into an empty database.
26. Open the Vercel URL. You should see the yellow demo banner and the five personas. Click **Start as Asha** and go through to disbursal. If the landing page shows "Waking up the demo server", wait; the free backend was asleep.

## Part E — GitHub secrets for the expiry job

The workflow `.github/workflows/expire.yml` runs every 6 hours. It signs in as admin and calls `POST /admin/jobs/expire`, which expires offers not e-signed within 7 days and applications abandoned for 30 days. It skips quietly until these secrets exist.

27. On GitHub, open the repository → **Settings** → **Secrets and variables** → **Actions**.
28. Click **New repository secret** and add these three:

    | Name | Value |
    |---|---|
    | `LENDWISE_API_URL` | the Render URL from step 13, no trailing slash |
    | `LENDWISE_ADMIN_USERNAME` | `admin` |
    | `LENDWISE_ADMIN_PASSWORD` | the `ADMIN_PASSWORD` from step 11 |

29. Test it: **Actions** tab → **Expire offers and abandoned applications** → **Run workflow** → `main`. The run should finish green, and its last step should print something like `{"expired_abandoned":0,"expired_offers":0}`.

GitHub pauses scheduled workflows after 60 days without commits; re-enable it from the Actions tab if that happens. Expiry also runs whenever an application is opened, so a pause only delays dashboard counts.

## Part F — Final checks

30. `https://<vercel-url>/internal/metrics` shows the funnel (500 started) and the time-in-stage chart labelled **Simulated timings**.
31. `https://<vercel-url>/internal/referrals` shows 110 referrals waiting, with names reduced to initials (read-only view).
32. On `/internal/policy`, click **Sign in to make changes** and sign in as `admin`. Then click **Reset demo data** and confirm. After the page reloads, the dashboard again shows 500 applications: reset restores the seed rather than emptying the system.
33. In the browser's developer console, there should be no CORS errors.

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Render logs: `Invalid configuration ... DATABASE_URL` | Missing or malformed. Paste the Neon string again (step 6). |
| Render logs: `ADMIN_PASSWORD still has the example value` | Production refuses `change-me` values. Choose a new password. |
| Render logs: `prepared statement ... does not exist`, or migrations hang | You used Neon's pooled (`-pooler`) host. Use the direct connection string (step 5). |
| Browser console: `blocked by CORS policy` | `CORS_ORIGINS` doesn't exactly match the site's origin. Check `https://`, no trailing slash, and the exact Vercel domain (step 24). |
| Frontend calls `http://localhost:8000` in production | `NEXT_PUBLIC_API_URL` wasn't set before the build. Set it and redeploy (step 20). |
| First visit takes up to a minute | The free Render service sleeps after about 15 idle minutes. The app shows a "Waking up the demo server" notice and retries. |
| Dashboard is empty after the first deploy | The database wasn't empty when the service first started (for example, from an earlier attempt), so the seed was skipped. Sign in as admin and click **Reset demo data**. |
| Phones from the seeded data can't sign in after changing `PII_HASH_KEY` | Seeded phone hashes use the key in force at load time. Click **Reset demo data** after changing the key. |
